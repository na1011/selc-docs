# [묶음] 에러·사유코드

> 유형: 기준정보 · 확인 담당: 미정(§9-2) · 원문 기준일 2026-11-02
> 이 묶음은 통합 에러코드, Reject와 그 사유코드(공통 사유코드), 그 밖의 사유코드에 대해 늘 참인 것만 담는다. 흐름·조건·순서는 프로세스 문서에 있다.

## 1. 범위
- 에러·사유 코드가 무엇을 식별하는지, 기준정보 항목, 원래 코드와의 맵핑, 이력 항목, Reject의 범위를 다룬다.
- 에러가 들어왔을 때 어떤 후속 처리를 하는지는 → P44 설비 에러·Reject 처리와 각 프로세스의 예외에 있다. 기준정보를 등록하는 화면은 → P47 기준정보 관리에 있다.
- 통합 에러코드와 공통 사유코드의 관계는 ⚠ 원문 불일치로 남아 있다(§3).

## 2. 용어
| 용어 | 뜻 | 동의어 | 비고 |
|---|---|---|---|
| Reject | 입고 과정에서 정상 입고할 수 없다고 판정된 화물 | REJECT, 리젝트 | 코드가 아니라 화물이다 |
| 공통 사유코드 | WCS가 정의하는 Reject 사유 코드 체계 | Reject 사유코드 | 통합 에러코드와의 관계는 §3 ⚠ |
| 통합 에러관리 | 설비사·설비마다 다른 에러코드를 WCS가 취합해 통합 에러코드로 관리하는 기능 | 통합 에러 관리 | |
| 통합 에러코드 | 통합 에러관리에서 WCS가 정의하는 공통 에러코드. 설비사별 원래 에러코드를 맵핑해 쓴다 | | |

## 3. 사실

### 무엇을 식별하나 (식별 기준)
- WCS는 설비사·설비별 에러코드를 통합 에러코드로 맵핑해 관리하는 통합 에러관리 기능을 제공한다
- ⚠ 원문 불일치: 설비 에러·Reject 사유는 통합 에러코드로 관리한다. Reject 사유코드(공통 사유코드)는 통합 에러코드의 한 분류(Reject 사유)로 같은 기준정보에서 관리하고, 설비사 원래 코드 → 공통 코드 맵핑 방식도 같다
- ⚠ 원문 불일치: 공통 사유코드는 WCS가 정의하는 Reject 사유 코드 체계다. 설비사별 원래 코드는 「Reject 사유코드 맵핑 기준정보」(설비사·원래 코드 → 공통 사유코드)로 공통 사유코드에 맵핑한다. 이 출처들은 통합 에러코드를 언급하지 않는다
- ⚠ 원문 불일치: 통합 에러관리 개요 쪽 기록은 Reject 사유코드(공통 사유코드)를 같은 기준정보 체계 안에서 관리하는 것을 「추천」으로 적는다. 같은 영역의 규칙은 확정 표현이다
- 출고 불가 사유코드는 표준화한다(예: 셀 이상, 팔레트 인출 불가, 재고 불일치, 설비 고장)
- 출고 불가 사유코드는 통합 에러코드의 설비 에러 분류로 관리하고, 별도 목록을 두지 않는다
- [확인필요] LOT 속성 변경 사유는 사유 코드(파손 등)로 관리한다

### 구성 항목
- 통합 에러코드마다 작업자 전달 메시지와 처리방법 메시지가 연결된다
- 통합 에러코드마다 분류와 등급이 있다

| 통합 에러 기준정보 | 항목 |
|---|---|
| ① 통합 에러코드 | 코드, 분류(설비 에러 / Reject 사유 / 인터페이스 오류 / 재고 오류), 등급(정보 / 경고 / 중대), 대상 설비 유형, 작업자 전달 메시지, 처리방법 메시지, 알림 대상(WCS PDA / 대시보드 / 파워유저), 반복 알림 억제 시간, 사용 여부 |
| ② 맵핑 | 설비사, 설비·호기 유형, 원래 에러코드, 원래 메시지 → 통합 에러코드 |
| ③ 등록·변경 이력 | |

- Reject 사유코드 맵핑 기준정보의 칸은 설비사·원래 코드 → 공통 사유코드다
- Reject 조치 유형은 공통 코드로 둔다: 재투입 / 수작업 영역 이동 / 보류 / 반품·폐기 요청 등

### 누가 만들고 어디서 오나
- 통합 에러코드와 공통 사유코드는 WCS가 정의한다
- Reject 사유코드 체계는 맵핑 체계다. 설비사별 원래 코드(ECS 에러 코드)는 그대로 받고, WCS 공통 사유코드에 맵핑해 관리한다
- Reject 사유코드는 ECS가 찾으면 ECS → WCS로, WCS가 찾으면 목적지 응답으로 WCS → ECS로 넘긴다
- WCS가 ECS에 넘기는 사유는 공통 사유코드로 한다
- Reject 화면 표시·집계는 공통 사유코드 기준으로 한다

### 사용 여부·이력
- 통합 에러코드에는 사용 여부가 있고, 기준정보의 등록·변경 이력을 남긴다
- Reject 이력에는 원래 코드와 공통 사유코드를 함께 남긴다

| 에러 이력 항목 |
|---|
| 원래 코드, 통합 코드 |
| 설비사·설비·호기 |
| 대상 ID, 발생 위치 |
| 관련 Task·Action |
| 발생·종료 시각 |
| 상태(발생 / 조치 중 / 종료) |
| 조치자·결과 |

| 공통 Reject 이력 항목 |
|---|
| 대상 구분(팔레트 / BOX), 대상 ID |
| 발생 구분(키워드·설비·설비사) |
| 판단 주체(ECS / WCS / 로지스올) |
| 사유코드(공통 사유코드 + 설비사 원래 코드) |
| W/T 연결 여부 |
| 발생 위치·시각 |
| 관련 작업 번호 |
| 상태(미처리 / 조치 중 / 완료) |

### 그 밖의 사실

#### Reject의 범위
- Reject는 Bypass와 구분한다
- 1층 입고대 Reject는 Bypass와 구분해 관리한다
- AS/RS 만재(용량 부족)로 3층 출고대에 배출하는 건(용량 부족 배출)도 Reject에 포함한다
- 이 건의 사유는 「용량 부족」이다

#### 사유 값
- Reject 사유코드에 「Product Code 불일치」가 있다
- 디베닝 REJECT 사유는 예정정보에 없는 제품, BCR 스캔 실패 등이다
- 사유 목록 전체는 아직 정해지지 않았다(§5 Q-169).

## 5. 미결

- [미결 Q-169] [추후 정리] Reject 공통 사유코드 목록(용량 부족 포함)과, 설비사(현대무벡스·로지스올, 디베닝 REJECT 사유 포함) 원래 코드의 맵핑 내용. 맵핑 체계로 한다는 것은 결정되어 있다
